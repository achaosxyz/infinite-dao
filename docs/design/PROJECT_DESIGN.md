# 项目核心设计

## 项目定位

《无限修仙 · 宗门纪》是面向单机玩家的 Windows x64 原生宗门经营模拟游戏。玩家选择六宗之一，决定长期战略、重点培养、护道人和关键议事，观察宗门在同一世界中发展。世界按月自动结算，支持暂停查看、存档恢复、流亡重建和消灭其他五宗后的统一终局。

本文与本目录的模块文档共同构成项目结构与设计的唯一事实来源（SSOT）。本文定义全局边界；模块文档细化已有模块的实现契约。`AGENTS.md` 只提供上下文摘要和开发行为约束，不替代设计文档。设计文档只描述当前实现，不记录历史、规划或 TODO。

## 当前技术与运行边界

- 客户端采用 Godot 4.7.2 .NET，业务代码使用 C#、`net10.0`；SDK 约束位于根目录 `global.json`。
- 默认解决方案为 `InfiniteDao.slnx`，包含六个源工程和三个 MSTest 测试工程。
- 游戏是单进程原生窗口，不依赖浏览器、本地 HTTP 游戏服务或数据库；存档是本地 JSON 文件。
- 项目采用根目录 `LICENSE` 中的 MIT 许可证，第三方组件保留各自许可；导出包携带项目许可证及 `licenses/` 中的 Godot/.NET 许可与第三方声明。
- 离线模式 `rules` 可完整游玩；智能模式 `llm` 通过 Anthropic Messages 和上下文计数接口运行后台 Agent。
- 默认地图为十二府192地域，六个宗门各有独立人物、资源、领地、外交和道统。
- 玩家输入以战略与选项为主，不提供手操战斗、自由自然语言执行命令或个人 RPG 装备栏。

## 模块划分

修改一个模块前，按本表只加载相关的 `MODULE.md`；跨模块变更再加载直接依赖模块，不一次性加载全部模块规范。

| 模块 | 真实代码位置 | 职责与详细契约 |
|---|---|---|
| Core | `src/InfiniteDao.Core/Game/` | 权威世界状态、命令校验和可复现规则；见 [CORE/MODULE.md](CORE/MODULE.md) |
| Agents | `src/InfiniteDao.Agents/` | Anthropic 配置、严格工具协议、Agent loop、公开记忆压缩与唤醒判断；见 [AGENTS/MODULE.md](AGENTS/MODULE.md) |
| Application | `src/InfiniteDao.Application/` | 会话、提交、后台任务调度、重试与离线转换；见 [APPLICATION/MODULE.md](APPLICATION/MODULE.md) |
| Infrastructure | `src/InfiniteDao.Infrastructure/Persistence/` | JSON 存档、导入验证与存档列表；见 [INFRASTRUCTURE/MODULE.md](INFRASTRUCTURE/MODULE.md) |
| Game | `src/InfiniteDao.Game/` | Godot 原生界面、地图、美术、时间控制与窗口验证；见 [GAME/MODULE.md](GAME/MODULE.md) |
| Simulator | `src/InfiniteDao.Simulator/` | 无网络的 LLM 本地配置检查 CLI；见 [SIMULATOR/MODULE.md](SIMULATOR/MODULE.md) |

实际工程依赖为：

```text
Game → Application → Core
                   → Agents → Core
                   → Infrastructure → Core
Simulator → Core + Agents + Infrastructure
```

Core 不引用表现层、HTTP 适配器或存档层。Agents 不负责写入世界事实；Infrastructure 不生成策略；Application 不另造一套战斗或经济规则。

`tests/` 包含 Core、Agents、Integration 三套 MSTest。`tools/` 提供构建启动、固定版本 Godot 安装、文档检查、Windows 导出与干净打包脚本。`.github/workflows/` 执行 develop/main 的提交检查和 main 的 Windows 连续构建发布；这些交付工具不属于游戏业务模块。完整目录及文档放置规则见 [STRUCTURE.md](../STRUCTURE.md)。

## 数据模型

运行中世界以 `Core/Game/GameState.cs` 的 `GameState` 为权威根对象；具体字段定义以源文件和对应模块文档核对。

| 数据结构 | 当前含义 |
|---|---|
| `GameState` | 种子、随机状态、提交版本、月份、玩家宗门、难度、模式、局终状态、统计及下列实体集合 |
| `Sect` | 山门、掌门、资源、安定、道藏、军阵、情报、战略、外交、覆灭和流亡状态 |
| `Region` | 唯一控制者、相邻地域、人口、矿产、灵材、灵脉、发展和护山阵 |
| `Cultivator` | 人物身份、年龄、六境修为、境龄、忠诚、伤势、生死、重点培养和护道人 |
| `GameEvent` / `EventChoice` | 当前待决议事、稳定选项身份、费用、规则说明和公开叙事 |
| `Campaign` | 发起者、守方、目标、时长、逐月军需、补给和参战门人 |
| `Expedition` | 历练者、实际随行护道人、目的地域、剩余月份与起因事件 |
| `BattleReport` | 个体交锋、伤害、境界倍率、参战者与死亡结果 |
| `Relic` | 法宝归属、战力效果、发现月份和来源事件 |
| `Chronicle` | 已发生事实、资源变化、相关宗门及历史因果引用 |
| `AgentDecision` | 已用于规则结算的方向、目标、公开理由及来源 |
| `SectAgentMemory` | 每宗独立计划、公开会话、摘要、归档、观察与复盘状态 |
| `SectAgentPlan` / `AgentConversationEntry` | 结构化战略意图与公开观察、提交记录；不保存隐藏思考 |
| `LlmConfiguration` | 本地连接、请求与运行参数；不属于游戏存档内容 |

后台任务、HTTP 客户端、取消源和任务代际属于会话运行态，不序列化进 `GameState`。完成的公开计划、调用统计、后台提示及离线模式会持久保存。存档槽为 `auto`、`one`、`two`、`three`。

## 关键流程

### 1. 接掌宗门与玩家操作

1. Godot 客户端接收宗门、种子、难度和运行模式，调用 Application 新建世界。
2. `WorldFactory` 生成地图、宗门、门人与开宗议事；玩家选择战略方向或处理事件。
3. `GameSession` 按提交版本检查操作，复制当前世界，再由 `GameEngine.Command` 校验并执行。
4. 成功结果自动存档后成为当前世界；人物、宗门和历史可随时查看。

### 2. 时间与世界演化

1. 自动时钟或手动推进触发逐月结算；待决议事、玩家流亡待重建和局终会阻止月结。
2. Application 收集已完成的后台结果，选择当前合法计划；模型未返回时维持宗门已有合法战略。
3. Core 按固定规则处理资源、供养、修炼、突破、寿元、历练、自动经营、战争和事件。
4. 完成月份后保存世界，再按当前情况调度需要唤醒的 Agent；不等待模型响应才能过月。
5. 玩家可暂停；窗口失焦暂停，浏览资料页本身不暂停。下拉菜单显示期间暂缓界面树重建。

### 3. 经营、成长与战争

- 玩家有五个战略方向，可重点培养至多三名门人，并安排更高境界的实际随行护道人。
- 灵石、灵材、修为、突破、历练、伤势、寿尽、战死和掌门继承由 Core 裁决。护道降低风险但不保证存活。
- 执事自动经营、招募和备战，采办与日常修炼保留供养和军需；资源不会由叙事凭空产生。
- 只能向接壤地域出征，战役持续多年并逐月消耗补给，断供会撤军。
- 战斗按实际门人交锋结算，境界、伤势、阵法、法宝、情报、战术、补给和战疲共同生效，不能仅比较总战力。
- 每个地域只有一个控制者，同一世界内的争夺不能重复结算。

### 4. 后台 Agent

1. 首次规划、重大变化、目标失效或到期复盘时，为相应敌宗启动独立后台任务；议事主持也走后台任务。
2. 每个任务读取独立快照与本宗公开记忆，通过工具查询并提交；单 Agent 内依赖步骤串行，跨 Agent 有界并行。
3. 默认并发上限10，不限制 Agent 总数或生命周期总调用次数。等待期间不持有世界提交锁。
4. 结果入队，由串行提交点按当前世界校验；失效目标不执行，迟到叙事不覆盖玩家已处理的事件。
5. 调用初次失败后按1/2/4秒退避重试3次，仍失败则明确切换离线、记录史书并取消其余任务；恢复智能世界需玩家手动操作。
6. 默认上下文256000 tokens，输入计数加预留输出达到90%时 compact。工具、记忆和计数细节见 Agents 模块。

有效计划的定期复盘从采纳月份计时，默认间隔60个月；公开记录保留观察月份。`PumpAgents` 只收集完成结果并调度任务，不等待模型、不增加回合提交版本；后续月结才执行新计划。新建或加载世界会取消并作废旧代际任务。

### 5. 存档、流亡和终局

1. 自动与手动存档经验证后写临时文件，再替换目标 JSON 文件。
2. 加载或导入先完成格式、实体、宗门定义和因果校验；成功提交后作废旧世界后台任务。
3. 玩家失去最后山门后，至多六名幸存门徒携道统流亡，通过薪火选择和落脚地选择在同一世界重建。
4. 可在无主地重建，也可赎买其他宗门的非山门地域；历史、年份、门徒身份与道统延续。
5. 消灭其他五宗的组织道统后进入统一终局；不要求杀尽所有人物或占领全部无主地。

### 6. 开发与 Windows 发布

1. 开发提交位于 `develop`，复查修复并通过 CI 后合并 `main`；两分支的 push 和目标为两分支的 PR 均触发 `CI`，检查状态关联到对应提交。
2. CI 使用 `global.json` 指定的 SDK，在 Windows 执行文档与脚本检查、离线测试和原生客户端编译。
3. `main` 的 push CI 成功后触发 Windows 发布；手动重跑也要求该确切提交已有成功的 main push CI。PR、fork 和 develop 的运行不能触发发布。
4. 发布检出通过 CI 的确切提交，从 Godot 官方固定版本安装 .NET 引擎和 Windows 模板，在新建隔离目录导出；不复用玩家便携目录。Godot 工具环境禁用 MSBuild 节点复用与后台服务器，避免导出结束后输出管道被后台节点占用。
5. `package-game.ps1` 排除本地配置与玩家数据，检查必需文件和自包含运行时，完成导出 EXE 的 headless 启动检查，再生成 ZIP 和 SHA256；headless 不代替真实窗口验收。
6. 只读构建任务上传产物，独立的最小写权限任务先创建草稿再发布 GitHub 预发行包。标签采用 `windows-运行号-重试号`，不虚构语义版本、不覆盖旧发布；正式版本号不由此流程推定。

## 一致性与安全边界

- 规则世界的随机状态随存档保存；智能世界还保存已采用意图，不能将模型输出宣称为仅由种子决定。
- 结构化提交仅来自严格原生工具；结构校验不能替代目标、费用和游戏效果的业务校验。
- 模型只能读取游戏快照并提出有限意图，不执行任意脚本，不直接写入资源、生死或战果。
- `config/llm.local.json`、连接密钥和玩家存档不进入 PCK；导出脚本不复制工作区私密配置。
- 隐藏思考只在当前工具回合内存中按协议回传，不进入公开会话、存档、UI 或日志。
- 常规构建、测试和配置检查不发送真实模型请求；`-VerifyModel` 是显式可能计费的联网验证。
